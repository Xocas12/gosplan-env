# `tests/golden/` — generated parity files (PLAN section 11, test T-B7)

This directory holds the **golden files**: seeded trajectories produced by the reference
implementation `ref/ref_step.py` and replayed by `test_golden_parity.py` against the production
environment. PLAN section 11 states the standard the comparison must meet — *implementation ==
reference to 1e-9 on seeded trajectories* — and finding F14 states the reason the files exist at
all: **numeric expectations are never hand-computed**. A hand-written expected value encodes the
author's belief about the dynamics; a generated one encodes the reference's behaviour, which is
independently reviewable and hand-checkable on the two-enterprise worked example in
`docs/ref_worked_example.md`.

Nothing in this directory is committed except this file, `.gitkeep` and the test itself:
`tests/golden/*.json` is git-ignored.

## What is in the matrix

PLAN section 11 fixes the matrix exactly:

| Axis | Values | Count |
|---|---|---|
| Configuration | the five of `ref.gen_golden.golden_configs()` | 5 |
| Environment seed | `GOLDEN_SEEDS = (0, 1, 2)`; `seed_policy = seed_env` per cell | 3 |
| Policy | `Random`, `TruthfulMyopic` (PLAN section 6.1) | 2 |
| Agent-steps per rollout | `GOLDEN_N_STEPS = 30` | — |

That is **30 documents**, one JSON file per (configuration, seed, policy) cell, named
`{config_name}__{agent}__seed{seed_env}.json`. The file name is for humans; the parity test parses
nothing out of it, because every field it needs is inside the document (`GOLDEN_SCHEMA` in
`ref/gen_golden.py`).

Each document carries the schema version, the `SPEC_VERSION` it was written against, the full
configuration and its hash, the observation layout (`obs_spec`), and one entry per agent-step with
the observation, the reward, the `done` flag, a SHA-256 digest of the reference state, and — at
REPORT steps — the three logged-only period scalars `val_measured`, `val_true` and `welfare`. Those
three are in the file **for parity only**: CONTRACT rule 6 keeps them out of every observation,
reward and agent input, which test T-B5 asserts with sentinels.

## How to generate them

```sh
make golden                 # the canonical form; invokes exactly the command below
python -m ref.gen_golden    # equivalent, run from the repository root
```

Both write all 30 files into this directory. Useful flags, all documented in `ref/gen_golden.py`:

```sh
python -m ref.gen_golden --check              # regenerate in memory, report differences, write nothing
python -m ref.gen_golden --out DIR            # write elsewhere
python -m ref.gen_golden --config NAME ...    # a subset — refused without --force
python -m ref.gen_golden --seed N ...         # a subset — refused without --force
python -m ref.gen_golden --steps N            # non-default length — refused without --force
```

A filtered or re-sized generation is refused without `--force` because *a set that is not the
pre-registered matrix is not a golden set*; `test_golden_matrix_is_complete` asserts the count for
the same reason. Generation is deterministic: two runs on the same checkout produce byte-identical
files, which is what makes `--check` meaningful and lets a reviewer confirm that a regeneration was
mechanical.

## What happens when they are absent

A fresh checkout has no golden files, because they are generated and git-ignored. In that state
`test_golden_parity.py` **skips** every test with a message naming `make golden` — it does not
fail. A missing golden set is a missing input, not a failing implementation.

The skip is also the reason a green suite on a fresh checkout is *not* evidence that T-B7 passes.
Before gate G0 (PLAN section 13, "full frozen suite green") the lead generates the files and runs
the suite with them present.

There is a second skip: if a document's `spec_version` differs from the current
`spec.SPEC_VERSION`, the test skips **loudly**, naming both versions. A stale golden set is
regenerated by the lead (see below), never silently accepted, and a comparison against an older
interface proves nothing either way.

## The freeze — CONTRACT rule 2

> **2. FROZEN TESTS.** `tests/unit`, `tests/behavioural` and `tests/golden` are read-only for
> implementers. If a test looks wrong, file an AMBIGUITY REPORT; do not edit it, do not skip it,
> and do not special-case the implementation to pass it.

Concretely, for this directory:

- an implementer **never** edits `test_golden_parity.py`;
- an implementer **never** edits a `*.json` document by hand — a hand-edited golden file is a
  fabricated oracle, and it is unfalsifiable afterwards;
- an implementer **never** deletes a document, and never regenerates one to clear a failure;
- an implementer **never** adds `--force` to a generation to make a smaller matrix pass;
- a golden failure is a bug in the implementation until the lead says otherwise. If the file looks
  wrong, the response is an AMBIGUITY REPORT (`workorders/AMBIGUITY_TEMPLATE.md`, CONTRACT rule 3),
  and the session ends there.

`ref/` itself is equally off limits to an implementer: it is written by **WO-002** (LEAD), it may
not import `gosplan/`, and it is validated by the property tests and by the hand-checkable
two-enterprise case in `docs/ref_worked_example.md`. That independence is what makes agreement
between `ref/` and `gosplan/` informative — two implementations that shared code would agree by
construction and prove nothing.

## Regeneration — WO-013 only

Golden files are regenerated **only** by the lead, at **WO-013 (Spec v1 freeze)**, or at a later
lead-owned change that alters the dynamics or the document layout. The procedure:

1. the dynamics, the state rendering of `ref_state_digest`, the observation layout, or
   `GOLDEN_SCHEMA` changed — the reason is written down first, not after;
2. `spec/CHANGELOG.md` gets an entry recording the version, the reason and the affected work orders
   (CONTRACT rule 1); the `SPEC_VERSION` bump lives in the same entry;
3. `make golden` regenerates all 30 documents;
4. the full frozen suite is re-run (`make test`);
5. the diff is reviewed: `python -m ref.gen_golden --check` on the previous checkout says which
   cells and which keys moved, and a regeneration whose diff is larger than the change explains is
   a finding, not a formality.

The generator prints this reminder on every successful run. It does **not** write the changelog
entry, run the suite or commit anything: those are lead decisions, and a generator that quietly
wrote the changelog for you would defeat the rule it exists to serve.
