## Implementation notes

Provisional until the lead revises the spec.

**Recomputation versus re-run — the one subtlety of this card.** A perturbed price vector may enter
in two ways, and the label on each output row says which:

```
recomputation   prices enter only the logged aggregates. Under objective_metric = "val" (and
                "quality_weighted", which reads q̂ and not prices) the fulfilment measure does not
                read plan_prices, so the existing ledger can simply be re-scored.
rerun           prices enter the fulfilment measure and therefore the reward. Under
                objective_metric = "net_output" (§2.9.2: m_i = R_i − Σ_j p_j · alloc_ij / p_{s(i)})
                the perturbed configuration is a DIFFERENT ENVIRONMENT and must be re-run.
```

The deciding field is `incentive.objective_metric` (`RERUN_TRIGGER_FIELD`). C_INC in PLAN §4.3 sets
`objective_metric → net_output`, so at least one Phase-3 arm takes the `rerun` path and the compute
for it must be budgeted rather than discovered.

`welfare_ratio` moves only through its denominator when `W_oracle` is itself price-weighted; every
table states which `W_oracle` it used — in Phase 1 the clearly labelled `W_truthful_max`
placeholder; from Phase 2 the expected-value MIP of PLAN §6.2, never the clairvoyant bound.

PLAN §2.10 additionally notes that the consumer CES weights `α_j` and elasticity `σ_c` are swept
**in this check, never in a treatment arm**. Whether this card performs that sweep as well, or only
the price perturbation, the revision must state.

What PLAN does **not** decide, and what the revision must state before this card is issued:

- the three fixed seeds (PLAN fixes that they are fixed and reused, not which integers; the module
  registers `(0, 1, 2)` and records them in the manifest);
- the enumeration of "every headline table" — the list must be explicit, or a table will be missed;
- whether the `α_j` / `σ_c` sweep of PLAN §2.10 belongs here or in its own block.

## Forbidden

- Re-scoring a run whose `objective_metric` reads prices. That is the `rerun` path, and skipping it
  would report a robustness check that was never performed.
- Suppressing, softening or footnoting a sign change in `specification_gap` (PLAN §§2.9.4, 7.5).
- Drawing fresh perturbations per table. The same three vectors go on every table, or the
  sensitivities are not comparable across tables.
- Applying a common scale factor instead of a per-good draw.
- Omitting a headline table because its sensitivity block is inconvenient, or because the metric was
  "obviously" price-insensitive. The check is standing, and it is a G4 pass condition.
- Letting any price-perturbed quantity reach an agent (rule 6): `welfare_true` and `val_measured`
  are logged and never observed.
- Computing any held-out phenomenon (PLAN §4.1 rows 2, 5, 6, 7) outside WO-030/WO-031.
- Running a gate from an implementer session (rule 13).

## Compute budget (PLAN §14)

No dedicated row. The `recomputation` path is free — it re-scores existing ledgers. The `rerun` path
costs one extra run per (arm, price vector) at `objective_metric = "net_output"`, i.e. up to three
times the arms that take it; budget it against the contrasts row ("5 × 30 | JAX | hours").
Delegation row: ≈40k tokens.
