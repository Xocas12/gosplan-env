Implementation notes

  1. DESIGN (PLAN section 5). Latin-hypercube sample of 500 points over
     `(beta, s, a*pen, lambda, psi, g, kappa, w)`: the seven continuous dimensions of `LHS_RANGES`
     (the PLAN section 3 registry ranges verbatim - `notch_height` [0.25, 2],
     `overfulfilment_slope` [0, 2], `audit_times_penalty` [0.05, 60], `ratchet_lambda` [0, 1],
     `tenure` [0.7, 0.98], `growth_directive` [0, 0.07], `effort_cost` [0.05, 0.5]) plus the eighth,
     discrete, stratified over `LHS_LEVELS["notch_width"] = (0.0, 0.25)` so both levels carry the
     same number of design points. The LHS seed defaults to `base_cfg.tech.seed_env`, is recorded in
     the table header and in every manifest, and makes the design reproducible point for point.

  2. PROCEDURE.
       a. Draw the design.
       b. Turn each point into an `EnvConfig` by overriding `incentive.notch_height`,
          `overfulfilment_slope`, `ratchet_lambda`, `tenure`, `growth_directive`, `effort_cost`,
          `notch_width`, plus `information.audit_rate` and `incentive.penalty_scale` under the
          factorisation convention the lead fixes (ambiguity 1). VALIDATE EVERY CONFIGURATION.
       c. Solve `solve_single_enterprise(cfg, DPGrid())` - PLAN section 5's grid, unchanged - and
          label it with `classify_regime`.
       d. Write `table.parquet` with EXACTLY `TABLE_COLUMNS`, then `regime.png` and `bhat.png`.
          Grid-edge hits are a regime signal: plotted and reported, never smoothed away.
       e. Write `candidates.md`, stating the "interior" definition used (ambiguity 2) next to every
          candidate.

  3. `audit_rate` IS DUAL-CLASSIFIED (INFO, and also entering the reward through the penalty; PLAN
     section 4.3). The table records `audit_rate` and `penalty_scale` ALONGSIDE their product, so
     the factorisation convention is legible from the file itself and the compound is never confused
     with either factor.

  4. COST (PLAN section 14). 500 configurations at about one CPU-minute each - about one hour on 8
     cores. Any process pool lives inside `main()`. `matplotlib` (the `viz` extra) and `pyarrow` are
     imported inside the functions that draw and write, never at module scope.

  5. EXIT CODE. `main()` returns 0 when the design was solved and all four artefacts were written
     with at least `MIN_BUNCHING_CANDIDATES` interior candidates. IT NEVER MEANS "GATE G1 PASSED":
     G1 is a human decision recorded in `runs/G1_decision.md`, taken after reading this map and
     BEFORE ANY TRAINING RUN.

OPEN - AMBIGUITIES FOR THIS SESSION (CONTRACT rule 3; do not silently choose)

  1. FACTORISATION OF `a * pen`. PLAN section 5 sweeps the compound, while `EnvConfig` carries
     `information.audit_rate` and `incentive.penalty_scale` separately. Two conventions fit the
     text: hold `audit_rate` at the registry value and set `penalty_scale = a_pen / audit_rate`; or
     sample both marginals inside their PLAN section 3 ranges and record the realised product. File
     an AMBIGUITY REPORT. Whichever the lead fixes is recorded in the manifest and printed in the
     table header (`run(...)["ap_factorisation"]`).
  2. "INTERIOR" OF THE BUNCHING REGION. PLAN section 5 asks the human to pick from the interior but
     defines no neighbourhood. Candidate definitions: every point within a fixed normalised
     parameter distance is also labelled `bunching`; or the k nearest neighbours in the
     Latin-hypercube design are. File an AMBIGUITY REPORT rather than choosing; the definition used
     is stated in `candidates.md` beside every candidate.
