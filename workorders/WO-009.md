Implementation notes

  1. SECTION 2.5 AS AN EXPLICIT STATE MACHINE. This is the defining requirement of the card. The
     eight stages are DATA, not control flow: `PeriodStage` (DELIVER 0, TRADE 1, PRODUCE 2, REPORT
     3, AUDIT 4, REWARD 5, TARGET 6, TERMINATE 7), `PERIOD_SCHEDULE` as the ordered tuple,
     `AGENT_STAGES = (PRODUCE, REPORT)`, and `stages_for_step(state, cfg)` as the transition
     function returning a CONTIGUOUS SLICE of `PERIOD_SCHEDULE`, with `M = cfg.incentive.
     steps_per_period`:

         k_step == 0,    phase "produce"   ->  (DELIVER, TRADE, PRODUCE)
         0 < k_step < M, phase "produce"   ->  (PRODUCE,)
         k_step == M,    phase "report"    ->  (REPORT, AUDIT, REWARD, TARGET, TERMINATE)

     `advance` executes exactly the stages `stages_for_step` returns, in that order, and nothing
     else. The schedule must be auditable by reading data, never inferred from the body of a step
     function - PLAN section 2.5 is titled "period schedule (typed)" for that reason, and finding
     F10 records the typed schedule with a separate REPORT step as the fix for the original
     sequencing ambiguity. `stage.value` orders the schedule and
     `PERIOD_SCHEDULE[stage.value] is stage`.

  2. AGENT-STEPS VERSUS STAGES. The agent acts `M + 1` times per period. DELIVER opens the period at
     the head of its first PRODUCE step and consumes the claims recorded at the PREVIOUS period's
     REPORT step. TRADE sits between DELIVER and PRODUCE because it reallocates the inputs DELIVER
     has just placed in `X`. AUDIT, REWARD, TARGET and TERMINATE follow the REPORT step with no
     further agent input.

  3. EACH STAGE FUNCTION IS A THIN ASSEMBLER. It calls the module that owns the arithmetic and
     threads `State` through. NO FORMULA OF PLAN SECTIONS 2.6 TO 2.11 MAY BE RESTATED IN THESE THREE
     FILES - production is `production.py`, planner rules and physical delivery `planner.py`,
     reporting/audit/penalty/bonus/reward/val/welfare `reporting.py` and `reward.py`, the
     observation `obs.py`, prices `prices.py`. Duplicating a formula here creates a second place for
     T-B7 to disagree with `ref/ref_step.py`.

  4. ORDERING THAT IS LOAD-BEARING. TARGET runs AFTER REWARD, so this period's bonus is judged
     against this period's own target (PLAN section 2.7.1). The holding loss is applied before the
     period's output is added at REPORT (`S <- (1 - h) * S + y`, sections 2.8 and 2.11) - inside
     `reporting.py`, called from `stage_report`. TERMINATE is last.

  5. HORIZON (section 2.12). Under `horizon_mode = "geometric"` the episode runs
     `cfg.tech.min_periods` periods unconditionally, then continues with probability
     `cfg.incentive.tenure` per period, hard cap `cfg.tech.max_periods`. ONE GLOBAL DRAW with
     purpose `terminate`, not a per-enterprise flag. `done` is the only channel by which the outcome
     reaches the learner; NO OBSERVATION FIELD CARRIES PERIODS REMAINING and none may proxy it
     (finding F4, T-B9). `tenure` is the economic INC parameter and is never conflated with the PPO
     discount `gamma`, which lives with the adapter (WO-017) and which the environment never reads.

  6. RNG (rule 9). Every stochastic term goes through `gosplan.rng.draw(seed_env, purpose,
     *indices)` with a purpose from the frozen `Purpose` literal. No `numpy.random`, no
     `jax.random`, no module-level generator anywhere under `gosplan/env/`. `seed_policy` is carried
     on the state as a separate stream and is never mixed into an environment draw.

  7. StepInfo IS NOT AGENT-FACING (rule 6). It carries `y`, `S`, `X`, the audit measurement and the
     period-level `val_measured`, `val_true` and `welfare`; it is written by the environment and
     read by `gosplan/metrics/ledger.py` and lead-run experiments only. `GosplanEnv.step` returns it
     BESIDE the observation, never inside it. The three period-level scalars are filled at the point
     of the schedule that defines them and are zero elsewhere: `val_measured` and `val_true` at
     REPORT, `welfare` after DELIVER, when `consumer` is known.

  8. REWARD IS A VECTOR (N,), with exactly the rule-4 terms: `-scale * c_ik` at a PRODUCE step,
     `scale * (B(rho) - 1[audited] * Pen + trade_surplus)` at the REPORT step, with
     `scale = reward_scale(cfg)` computed once analytically. No shaping, no auxiliary term, no
     running normalisation, no per-step bonus of any other kind.

  9. ACTIONS. `action_spec(cfg)` returns all six dimensions with the PLAN section 2.3 bounds;
     `active_action_dims(cfg)` returns `["effort", "report_ratio", "input_request"]` at
     `p1_default_config()` and must be a pure function of the configuration that does not change
     within a run. Dimensions irrelevant to the current stage are IGNORED, never rejected, and the
     environment never trusts an agent to have masked them itself. `input_request` arrives as a
     multiple of need and is rescaled and clipped against the current `need_ij` when read.

  10. GOLDEN FILES. `tests/golden/*.json` is git-ignored and generated from the frozen reference. If
      the directory holds only `.gitkeep`, generate the set once with the unmodified generator
      (`uv run python -m ref.gen_golden`, no arguments - the pre-registered matrix, 5 configs x 3
      seeds x 2 agents = 30 files, 30 agent-steps each). NEVER REGENERATE THEM TO MAKE A FAILING
      PARITY TEST PASS: a mismatch is a bug in `gosplan/env/`, and WO-013 is the only card that
      regenerates after a deliberate dynamics change. Never `--force`, never a restricted filter.

Forbidden

  - Restating any formula of PLAN sections 2.6 to 2.11 inside `step.py`, `env.py` or `state.py`.
  - Any `numpy.random` or `jax.random` call, or any module-level global generator, under
    `gosplan/env/` (rule 9).
  - Any agent-facing use of `StepInfo`; any true quantity reaching an observation or a reward
    (rules 5, 6). `make_planner_view` and `build_observation` remain the only sanctioned readers of
    `State` on someone else's behalf.
  - Adding, shaping, normalising or rescaling a reward term; any running reward normalisation
    (rule 4).
  - Implementing bunching, padding, storming, hoarding, shaving or trade as a transition rule
    (rule 7). The stages call rules; the phenomena are consequences of those rules or they are not
    results at all.
  - Widening or narrowing `report_max_ratio`, the inventory cap, or any other bound to make a test
    pass (rule 8).
  - Reordering `PERIOD_SCHEDULE`, or changing `PeriodStage` values, without a lead decision - it
    changes the dynamics and invalidates every golden file.
  - Editing `ref/`, `spec/spec.py`, any test file, `PLAN.md`, or any file not on the "Write only"
    list, including "obvious" one-line fixes in `production.py` or `planner.py`. A defect found
    there is an AMBIGUITY REPORT naming the owning work order.
  - Running anything in `tests/acceptance/` (rule 13).
