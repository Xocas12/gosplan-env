Acceptance criteria PLAN §6.3 already fixes:

- freeze `N − 1` learned policies from the arm under audit; train **one** fresh best-responder
  (`N_BEST_RESPONDERS = 1`) with the **same PPO configuration and the same budget** — not a longer
  run, not a different learning rate, not a different reward scale;
- report `(R_BR − R_pop) / |R_pop|` **per seed**, not only its mean;
- compare against the threshold, whose provisional value is 5% and whose status is "finalised by the
  lead at G3". The harness reads it as a parameter and records the value used in the manifest, so a
  later change of threshold cannot silently re-label an old run;
- an arm above the threshold is written out with the `NON-CONVERGED` label and is **reported as
  non-converged, not as a result**. The harness must make that label impossible to lose: it belongs
  in the table, in the report and in the manifest flags.

## Implementation notes

Provisional until the lead revises the spec.

`R_pop` is the frozen population's own return over the measurement window of PLAN §4.4 (`t ≥ 2`),
under common random numbers with the best-responder run (shared `seed_env`), so the difference is
not a noise draw. `R_BR` is the fresh best-responder's return in the same environment with the other
`N − 1` policies frozen.

CONTRACT rule 4 applies to the best-responder exactly as it does to the population: the same
`reward_scale(cfg)`, no reward normalisation, per-batch advantage normalisation only. An
exploitability number computed under a different reward is not an exploitability number.

What PLAN does **not** decide, and what the revision must state before this card is issued:

- which enterprise index is replaced by the best-responder, and whether the result is averaged over
  several choices of index — with `param_sharing = "shared"` the population is one policy, so the
  choice may or may not matter, and the answer is a design decision, not a default;
- how many seeds the harness runs per arm (PLAN §14 says only "per arm × seeds, same budget as a
  run");
- whether the best-responder inherits the population's initialisation or starts fresh — PLAN says
  *fresh*, which the harness must not quietly soften into a warm start;
- the aggregation reported next to the per-seed numbers (PLAN §4.3's IQM with stratified bootstrap
  CIs is specified for contrasts, not stated here).

## Forbidden

- Choosing or changing the threshold. It is the lead's at G3; this harness reads it and records it
  (`THRESHOLD_STATUS` says so in the module).
- Reporting an arm above the threshold as a result, or dropping it silently. It is reported, with
  its label.
- Giving the best-responder a longer budget, a different PPO configuration, a shaped reward, or a
  reward normalisation (CONTRACT rule 4).
- Running any gate experiment from here (rule 13): this card writes a harness; the lead runs it.
- Computing PLAN §4.1 rows **2, 5, 6, 7** — held out until WO-030.

The harness must therefore be runnable arm-by-arm and must checkpoint, so a doubled budget is
spendable incrementally. Delegation row: ≈40k tokens.
