Implementation notes

  1. THE SECTION 4.5 SETTINGS ARE PRE-REGISTRATION DATA, hard-coded as defaults and recorded in the
     manifest. They already exist as module constants; use them as the defaults of
     `phenomenon_bunching` and pass them through to the estimator:

         bin width            0.005              BUNCHING_BIN_WIDTH
         fitted range         rho in [0.6, 1.4]  BUNCHING_WINDOW_LO / _HI
         excluded window      [0.95, 1.02]       BUNCHING_EXCL_LO / _HI
         polynomial degree    7                  BUNCHING_POLY_DEGREE
         excess-mass window   [1.00, 1.02]       BUNCHING_EXCESS_LO / _HI
         hole window          [0.95, 1.00)       BUNCHING_HOLE_LO / _HI
         SE                   bootstrap over SEEDS (the seed is the resampling unit)

         b_hat = (observed - counterfactual mass in the excess window)
                 / (mean counterfactual density in that window)
         hole mass = the same computation on the hole window

     `write_manifest`'s `bunching_settings` field carries exactly these values for every run
     (rule 10). They have ONE HOME - this module - and no experiment restates them. They are not
     tuning knobs: the sensitivity of `b_hat` to them is itself a reported result of the
     estimator-bias study of PLAN section 7.2, which sweeps a grid AROUND these values without
     changing them here.

  2. ROW 1 - FULFILMENT BUNCHING (pipeline check). Excess mass of `rho_report` in [1.00, 1.02]
     against a degree-7 polynomial counterfactual fitted OUTSIDE the excluded window, with the hole
     mass on [0.95, 1.00) reported alongside. Estimator: `forensics_core.bunching` where installed,
     the vendored fallback otherwise. Its appearance is NOT evidence for Claim A - if bunching fails
     to appear the optimiser is broken, and that is all this row certifies.

  3. ROW 4 - PADDING (pipeline check). `mean_i max(0, R_i - S_i) / T_i`, with the elasticity with
     respect to `a*pen` compared to the DP's prediction. The comparison itself is WO-019's and
     WO-020's; this module supplies the statistic.

  4. MEASUREMENT WINDOW (section 4.4). Periods `t >= 2` only (`MEASUREMENT_FIRST_PERIOD`); NO
     end-of-episode exclusion under geometric termination (`MEASUREMENT_EXCLUDE_EPISODE_END =
     False`); reports at `rho_max` INCLUDED AND FLAGGED, never winsorised, trimmed or dropped
     (`MEASUREMENT_INCLUDE_AT_BOUND = True`, rule 8). Every phenomenon that reads reports also
     reports `at_bound_frac`. The window is applied by this reader, never by the ledger writer.

  5. `resolve_estimators` IS THE ONLY PLACE `forensics_core` MAY BE IMPORTED, and only inside a
     `try/except ImportError` that falls back to `gosplan.metrics._fallback`, exactly as PLAN
     section 7.3 specifies. The skeleton spells the resolution out; implement it as written.
     Consequences the design leans on: the two surfaces are interchangeable, so `phenomena.py` is
     written ONCE; the fallback is never a silent substitute, because every run records
     `estimator_backend` and `estimator_version`; and importing `gosplan.metrics` never depends on a
     package installed from a sibling checkout. The import is not at module scope, anywhere.

  6. THE FALLBACK SIGNATURES ARE FROZEN BY PLAN SECTION 7.3 and must not move - argument names and
     order included:

         estimate(x, window_lo, window_hi, bin_width, degree, excl_lo, excl_hi) -> BunchingResult
         ledger_test(reported_supply, received_inputs, io_matrix, prices)       -> ReconResult
         cross_section(values, groups)                                          -> DispersionResult

     The excess and hole windows are the CALLER'S pre-registration constants; they are not arguments
     of the frozen signature and must not be inferred from `excl_lo` / `excl_hi`.
     `numpy.polynomial.polynomial.Polynomial.fit` on the retained bins is enough - no `scipy` at
     module scope. Bump `FALLBACK_ESTIMATOR_VERSION` if anything changes - a signature, a result
     field or an estimator's arithmetic - because a `b_hat` computed under one version is not
     comparable with one computed under another.

  7. CONSISTENCY WITH THE DP. `gosplan.agents.dp.dp_excess_mass` computes `b_hat_DP` under the same
     section 4.5 settings. The two must give the same number on the same sample; a divergence is a
     bug and an AMBIGUITY REPORT (you may not edit `dp.py`).

  8. SCOPE OF THE COUPLING (PLAN section 7.3), restated so it cannot drift. OUT: digit tests (RL
     policies have no digit preferences, finding F12); any claim of CALIBRATION of archival
     detectors; any use of Phase-1 output for the archival anchor. IN: bunching-bias curves,
     reconciliation power curves, dispersion behaviour under known cross-sectional distortion, and
     the Phase-2 ministry-level series.
