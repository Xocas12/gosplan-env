6. **Hygiene**, as in the Phase-1 gate: the `BOUND_BINDING` flag (CONTRACT rule 8) reported wherever

## Implementation notes

Provisional until the lead revises the spec.

Structure the report as **one pass/fail line per G3 condition**, exactly as `phase1_gate.py` does
for the four G2 criteria, followed by the numbers. A gate report whose conclusion has to be inferred
from a table is a gate report that can be misread.

**Common random numbers.** Every held-out phenomenon defined against a truthful-myopic baseline
(rows 2 and 5) needs that baseline run under **the same `seed_env`** (PLAN §§4.1, 4.3). Budget both
legs.

**Measurement window (PLAN §4.4):** periods `t ≥ 2`; no end-of-episode exclusion; reports at `ρ_max`
included and flagged.

**Manifest (CONTRACT rule 10):** every run writes `runs/<hash>/manifest.json` with config hash, spec
version, git hash, seeds, reference-PPO version, estimator version and backend, LLM model ids and
versions, solver version and optimality gap, and flags. The roll-up in the report cites the hashes,
so every headline number is traceable to a manifest.

What PLAN does **not** decide, and what the revision must state before this card is issued:

- the acceptance configuration list. PLAN §14 budgets "≈8 configs × 30 seeds"; which eight, and
  which arms carry an active ministry, trade, or an LLM ministry, is the revision's;
- whether the LLM ministry study (PLAN §7.4, WO-035) contributes anything to G3 — PLAN §13 lists it
  under G4, not G3;
- the C0 Phase-2 configuration that PLAN §4.3 refers to as "post-G3 values", which this run is what
  produces.

## Forbidden

- Computing any held-out phenomenon anywhere but here, and here only on the PLAN §4.2 locked values.
- Making a phenomenon appear. PLAN §4.2: *"If a held-out phenomenon fails to appear, the result is
  reported as a failure."* PLAN §13: *"A gate that fails produces a written failure report; the next
  work order is a lead diagnosis, never a parameter change to make the gate pass. Parameter changes
  after G1 create a new, labelled study."*
- Reporting an arm whose exploitability exceeds the threshold as a result.
- Using the clairvoyant bound as `W_oracle`, or reporting either unlabelled.
- Widening or narrowing `ρ_max` to clear a `BOUND_BINDING` flag (CONTRACT rule 8).
- Running the gate from an implementer session (rule 13). This card writes the harness.
- Adding a reward term, an observation field or a transition rule (rules 4, 6, 7).
