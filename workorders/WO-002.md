Implementation notes

  `ref/ref_step.py` is the oracle for the golden files, so it is written for readability and not
  for speed: pure Python, explicit loops, no vectorisation, `N <= 4`. It realises PLAN sections
  2.5-2.11 - the period schedule DELIVER, PRODUCE x M, REPORT, AUDIT, REWARD, TARGET, TERMINATE;
  the production and coverage formulas; the four planner rules; reporting, audit, penalty, bonus;
  reward and the logged metrics; prices; inventory with the holding loss and the cap. It uses the
  same key-based RNG construction as `gosplan/rng.py` so that a seeded trajectory is reproducible
  across both implementations - key-based draws are order-independent, which is exactly what makes
  a reference comparison meaningful (PLAN section 2.15).

  Numeric expectations are never hand-computed (review finding F14). `ref/gen_golden.py` produces
  5 configurations x 3 seeds x 30 agent-steps with `Random` and `TruthfulMyopic`, and the golden
  parity test compares the implementation against those files to 1e-9. The reference itself is
  validated only two ways: by the property tests, and by the hand-checkable two-enterprise,
  two-sector case committed as `docs/ref_worked_example.md`. Write that worked example as numbers
  a human can follow step by step, not as a narrative.

  Test-writing discipline, because rule 2 makes each of these permanent:
    - A test asserts what PLAN says, at the tolerance PLAN states, and nothing more. Where PLAN
      states no tolerance, state the one chosen in the test's docstring and justify it there.
    - A test must not encode a convention the spec does not state. If writing an assertion requires
      inventing one - the value of `poolfill_j` when a sector's claims are all zero, the behaviour
      of `reward_scale` when `B_cfg(1.1)` is zero, the RNG purpose for the price perturbation -
      resolve it in `spec/spec.py` or in the relevant card first (that is WO-001 or a spec change),
      or file an AMBIGUITY REPORT. Do not resolve it silently inside a test.
    - Behavioural tests drive HEURISTIC agents, never a trained policy, and never assert the
      direction of a held-out phenomenon. T-B3 asserts shortage propagation; it does NOT assert the
      direction of hoarding, which is held out (PLAN sections 4.1, 4.2).
    - T-B1 is the rule-7 test: under (w = 0.25, rho_cap = inf, a = 1, pen = 200, g = 0),
      `TruthfulMyopic` reports stock to 1e-9; its rho histogram has no bin above 3x the mean of its
      two neighbours; within-period effort Gini equals what yield noise alone implies under uniform
      delivery; no trade; requests equal need. Passing it is necessary, not sufficient - the lead
      still reviews every `env/` diff against rule 7.
    - `tests/acceptance/` gets nothing from this card. CONTRACT rule 13: it holds lead-run gate
      experiments, is on no must-pass list, and is excluded from `testpaths`.

Forbidden

  - Any use of `gosplan/` from `ref/`. The reference must be independently derived from PLAN
    sections 2.5-2.11, or it cannot be evidence about the implementation. This includes importing
    `gosplan.config` for the defaults: restate them in `ref/`.
  - Vectorising, optimising or generalising `ref/ref_step.py` beyond `N <= 4`.
  - Writing any test into `tests/acceptance/` (CONTRACT rule 13).
  - Writing any implementation body under `gosplan/`, or editing any file not on the "Write only"
    list.
  - Hand-computing an expected trajectory value into a test instead of generating it from `ref/`.
  - Asserting anything about phenomena 2, 5, 6 or 7 of PLAN section 4.1: they are held out, and
    computing them before Phase 2 is forbidden by the WO-012 and WO-016 cards too.
  - Encoding, in any test, a reward term that CONTRACT rule 4 does not permit, a planner function
    that takes a `State` (rule 5), or an observation carrying a rule-6 quantity - even as a
    negative example fixture that a later refactor might promote to production.
