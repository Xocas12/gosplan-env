Implementation notes

  1. HEADS ONLY FOR `active_action_dims(cfg)` - `["effort", "report_ratio", "input_request"]` at
     `p1_default_config()`. Inactive dimensions get NO PARAMETERS AT ALL, which is why
     `active_action_dims` must be a pure function of the configuration and must not change within a
     run.

  2. TANH-SQUASHED GAUSSIAN. Each head emits `(mean, log_std)` in pre-squash space; the action is
     `tanh`-squashed and affinely mapped onto that dimension's box from `action_spec(cfg)`, so
     bounds hold BY CONSTRUCTION, never by clipping after the fact, and the log-probability carries
     the `log(1 - tanh(z)**2)` Jacobian correction.

  3. REPORT HEAD INITIALISED AT rho = 1, STD 0.05 (PLAN section 6.1). The initialisation is
     specified in RATIO units, so push it through the squash: with box `[lo, hi]` and
     `a(z) = lo + (hi - lo) * (tanh(z) + 1) / 2`, the bias solves `a(z0) = 1`, i.e.
     `z0 = atanh(2 * (1 - lo) / (hi - lo) - 1)`, and the initial log-std is set so that the induced
     standard deviation in ratio units,
     `|da/dz|(z0) * sigma_z = (hi - lo) / 2 * (1 - tanh(z0)**2) * sigma_z`, equals
     `PPOConfig.report_head_init_std`. WHY IT MATTERS: a policy initialised at `rho = 1` starts ON
     the notch of section 2.8, so the discontinuity is inside the initial exploration support and
     bunching is neither seeded nor made unreachable.

  4. SECTOR ONE-HOT HANDLED BY `param_sharing`. At `cfg.tech.param_sharing == "shared"` (Phase 1)
     there is one policy for all `N` enterprises and sector identity enters ONLY through the one-hot
     block of the observation (`obs_spec` indices `12 + J : 12 + 2J`). `"per_sector"` builds one
     parameter set per sector, `"independent"` one per enterprise. The adapter chooses the
     structure; IT NEVER EDITS THE OBSERVATION.

  5. FIXED ANALYTIC REWARD SCALE; NO REWARD NORMALISATION (rule 4).
     `scale = reward_scale(cfg) = 1 / B_cfg(1.1)` is computed once from the configuration and the
     environment HAS ALREADY APPLIED IT to the reward the adapter receives; the adapter never
     rescales a reward again. Concretely the wrapped object must carry NO `RunningMeanStd` on
     rewards or returns, NO `NormalizeReward` wrapper, and NO return-scaling option left at its
     library default. Reference implementations ship these ON by default, so switching them off is a
     positive step you take, and the frozen test verifies it by inspecting the wrapped object.
     Observation normalisation is a separate question, is not what rule 4 forbids, and whatever is
     chosen is recorded in the manifest.

  6. PER-BATCH ADVANTAGE NORMALISATION IS PERMITTED (rule 4, explicitly) and is on by default
     (`PPOConfig.normalise_advantages`). There is deliberately no corresponding
     reward-normalisation field: rule 4 forbids it outright, so it is not a configurable choice and
     cannot be switched on from a config file.

  7. gamma = 0.99, lambda_GAE = 0.97 (PLAN section 6.1), lr 3e-4, clip 0.2, entropy 0.01 -> 0.001
     (the schedule itself lives in `train.py`, WO-018). `gamma` is the TECHNICAL discount and is
     distinct from the ECONOMIC continuation probability `psi = cfg.incentive.tenure` (section
     2.12): the environment terminates geometrically at `psi`, the learner discounts at `gamma`, and
     the single-enterprise DP uses `psi * gamma` (`gosplan.agents.dp.DP_DISCOUNT`). G2 criterion 1
     compares the DP and PPO at the same effective discount, so conflating the two silently breaks
     the gate.

  8. PHASE-AWARE MASKING. At a PRODUCE step only `effort` (Phase 2: `quality`, `invest`); at the
     REPORT step only `report_ratio` and `input_request` (Phase 2: `trade_offer`). Inactive heads
     are masked per step so their log-probabilities and entropies do not enter that step's loss. The
     environment ignores irrelevant dimensions anyway (section 2.3), so masking is about credit
     assignment, not legality.

  9. `forward` TAKES `obs` ONLY (rule 6). No `State`, no `StepInfo`, no `PlannerView`, no
     `welfare_true`, no `val_measured`, no other enterprise's true quantities. T-B5 inspects the
     signature, so the argument list is part of the interface.

  10. `manifest_entry` returns every `PPOConfig` field plus the resolved reference identity for the
      rule-10 manifest, `reference_ppo_version` above all. A missing field there is a bug, never an
      ambiguity.

Forbidden

  - Any running reward normalisation, reward clipping, reward shaping, auxiliary, curiosity or
    potential-based term, or return scaling - anywhere in the adapter or in the object it wraps
    (rule 4).
  - Any input to `forward` other than `obs`; any read of `StepInfo`, `State`, `PlannerView`,
    `welfare_true` or `val_measured` (rules 5, 6).
  - Implementing PPO from scratch, vendoring a copy into this repository, or leaving
    `reference_impl` / `reference_version` unset.
  - Building a head for an inactive dimension, or letting `head_names` change within a run.
  - Clipping actions into bounds after sampling instead of squashing; changing an `action_spec`
    bound, `report_max_ratio` included (rule 8).
  - Editing the observation, adding a feature to it, or introducing sector identity by any route
    other than the existing one-hot block.
  - Changing `gamma`, `lambda_GAE`, the learning rate, the clip coefficient or the entropy
    endpoints. They are TECH constants, fixed across every treatment arm (PLAN section 3).
  - Editing `gosplan/env/`, `gosplan/agents/ppo/train.py`, `tests/`, `ref/`, `spec/spec.py` or
    `PLAN.md`. Running `tests/acceptance/` (rule 13).
